# Wave Race 64 implementation audit

## Executive finding

Claude did not invent the static Wave Race 64 core. The repository contains a 1,203-function host oracle produced from the US Rev 1 recompile, a headless runtime, real cartridge DMA, controller injection, overlay dispatch, and an independent interpreter comparison. The repaired host oracle has bit-exact authoritative environment state for one pinned trace through a native failure terminal. Production now uses a generated CUDA racing closure containing 511 game functions, 6 device runtime shims, and 510 indirect-dispatch entries.

Several original claims around that core were materially wrong or unsupported. The ASCII screen was presented like a playable Wave Race display even though it contained no game pixels. Its original position, heading, progress, and gate telemetry came from RAM scans that were later retracted. The display used 60 Hz for a 20 Hz game-update path, labeled B as a brake, and allowed an unresolved indirect call to become a no-op. The first Puffer integration lived in a package whose own `pyproject.toml` said version `4.0.0`, despite its `pufferlib-5.0-lavin` directory name. At the time of that demo and the first repaired adapter, simulation ran on host CPU. That historical statement no longer describes production.

The current defensible conclusion is materially stronger but still scoped. Production is a native PufferLib 5.0 `PUF_GPU` environment with a generated device racing closure, a 57-value control observation, dynamic local wave samples, native speed and power, device-resident reset and autoreset, and a human-readable eval-only renderer. The accepted 4,096-agent run fine-tuned the prior accepted policy for 10,485,760 steps on the frozen production executable at 81,425.088136 standard Puffer SPS. GPU utilization was 96%; whole-process CPU averaged 9% of one core, including startup. The accepted checkpoint completed 128/128 deterministic official three-lap races on wave seeds 2902 and 16902 with no failure, disqualification, timeout, or environment fault. CPU is still used for cartridge boot and pool construction at startup, plus logging, checkpointing, and rendering. Broad game parity remains unproven, and earlier OBS43 and OBS55 checkpoints remain incompatible.

## Original assignment

The human assignment required:

1. a native Wave Race 64 core capable of running inside PufferLib;
2. actual-game parity rather than a loose proxy;
3. high training throughput;
4. integration with the current PufferLib 5.0 native stack;
5. a CUDA simulator, if feasible, so simulation would not consume host CPU.

The later stop-hook feedback explicitly rejected partial completion of the first three items. A core that runs and trains at low or unmeasured throughput does not satisfy the high-throughput goal.

## Evidence hierarchy

This audit gives evidence weight in the following order:

1. decompilation-derived structures and constants for the exact ROM revision;
2. frame-aligned output from an independent Mupen64Plus pure interpreter;
3. the final CPU-oracle/device transition contract, CUDA stress, VMM isolation, and deterministic replay tests;
4. native-CUDA training under the accepted transition contract and fresh evaluation tied to the hashed checkpoint;
5. current implementation source, generated-closure census, build flags, and PufferLib backend contract;
6. historical CPU-backend training, RAM scans, terminal plots, and short runs.

The [official Nintendo controller page](https://www.nintendo.com/eu/media/downloads/games_8/emanuals/nintendo_8/Manual_Nintendo64_WaveRace64_EN.pdf#page=5) is authoritative for player-facing input semantics. It defines A as throttle, B as wave damping, R as sliding, and the stick as handling and center-of-gravity control. Z duplicates A throttle.

## Parity evidence and boundary

The independent oracle pins:

- Wave Race 64 US Rev 1, 8,388,608 bytes, SHA-256 `f35d2423ebcb86eaf86fa935b613c7532b123a7bc50fb74996984c3b02fc3999`;
- Mupen64Plus pure interpreter commit `6dca4c15370ac3e2171ce7b31426695f8f39b460`;
- RSP HLE commit `8a7a472a7172eb2c8725b305eae26818ed7b51a2`;
- real menu selection of Time Trials, rider confirmation, Sunny Beach, two neutral updates, then a fixed held-A trace.

Two 2,400-VI interpreter repeats were internally identical. Two static repeats were internally identical. After dropping one extra pre-game interpreter controller scan, 638 scans align from guest frame 0 through 637.

Both engines produce the same route sequence:

| Guest frame | Lap | Target node | Misses | Game state |
| ---: | ---: | ---: | ---: | ---: |
| 214 | 0 | 0 | 0 | `0x28` |
| 248 | 1 | 2 | 0 | `0x28` |
| 325 | 1 | 4 | 0 | `0x28` |
| 368 | 1 | 9 | 1 | `0x28` |
| 637 | 1 | 9 | 1 | `0x29` |

Primary RNG, active physics position/heading/speed bits, rider route state, official outcome flags, recovery, mode identity, and controller inputs are bit-exact across all aligned scans. The runtime originally returned zero from the cartridge's first `osGetTime`, selecting a different primary physics RNG stream. Recovering the interpreter value `0x56D84BE4` by inverting the common cartridge LCG and using it for the first boot-time call repaired the discrepancy.

The proof remains trace-specific. The secondary `Math_Rand` state at `0x80226F00` differs at guest frame 2 because the headless runtime does not model post-reset time advancement. No listed authoritative field changed through frame 637. Graphics, audio, every writable byte, successful three-lap completion, and alternate action regimes remain unproven.

The new pure water sampler has a separate, narrower exactness result. The checked-in adapter harness compares `wr64_water_height` bit-for-bit with the recompiled cartridge function `func_8004D30C` at 4,096 deterministic live-field points, covers both interpolation branches, and confirms that the pure query leaves live RDRAM unchanged. A separate implementation characterization compared 262,144 points across 64 randomized complete water fields with zero float-bit mismatches under `-ffp-contract=off`. This validates the translation against the recompiled function. It is not an independent Mupen comparison of the water grid's evolution and does not widen the trace-level game parity claim. An A/B intervention that flattened the live water field diverged from the authoritative baseline by the second guest update, proving that waves affect simulation rather than only presentation.

Direct reset-time calls to `func_8004F790` were rejected after instrumentation showed they do not reproduce the live race-start distribution. The active snapshot follows the final generator call with 57 complete native update-chain calls and contains scripted large waves, nonzero water velocities, rider contact, and related RNG state. Replaying only the low-level generator or water update produced materially narrower height ranges and an incoherent combination of new water with fixed rider state.

Production builds `wave_variants` complete cartridge boots through the exact mode-state-2 race-start boundary on the host. A deterministic tested transform of `wave_seed` and variant index, using fixed index salt `0xB9DCF3C0`, changes the initial `osGetTime` value. Seed pairs 42/902 and 902/2902 each produced 128 unique boot-time, full-RDRAM, and complete-water hashes per seed with zero cross-seed overlap. CUDA startup stages every complete donor, validates route and snapshot invariants, hash-and-byte rejects duplicate full RDRAM or complete water fields, packs changed 4 KiB pages, reconstructs every variant page-by-page, and uploads canonical RDRAM, page deltas, and machine scalars. The production constructor is not streamed.

The retained all-128 seed-902 host acceptance sweep remains pool-oracle evidence. It compared every reconstructed owner with a sequential native donor on complete 8 MiB reset RDRAM, `State`, all 57 observations, transition buffers, render projection, and host-visible machine scalars, then compared two 32-decision scripts per variant. Current CUDA startup reproduced the same validation class for K=128 and packed 15,464 pages, or 63,340,544 bytes. The CUDA contract passed authentic reset projection, and the stress test passed deterministic replay, all 16 configured stress variants, 1,600 autoresets, and one-environment perturbation isolation. These results establish coherent reset variants and deterministic reconstruction, not independent interpreter parity for every variant.

The host oracle's floating-point scope canonicalizes AArch64 FPCR and retains hostile-FPCR regression coverage. CUDA has a separate numerical acceptance boundary: 225,720 compared floating outputs, 1,645 non-bitwise values, maximum absolute error `1.78814e-07`, and maximum ULP distance 3. Its byte-level scope covers 13 selected authoritative rider fields plus separately enumerated physics, helper, water, and game-state regions. Renderer-only rider byte `0x308` is outside that selected scope and has no training effect.

The evaluator capture has also been tested as a read-only state projection. Two captures must have identical logical content and hashes, every captured course pass point must match the adapter geometry, every one of the 1,089 water values must match `wr64_water_height` bit-for-bit, native clocks, speed, and power must match live game fields, live RDRAM must remain unchanged, and capture without rendering must leave `env->client` null. ## PufferLib 5.0 design review

The production adapter follows the same native GPU design used by first-party CUDA Breakout and Robot Arm:

- `#define PUF_BACKEND PUF_GPU` selects the batch API in `pufferenv.h`;
- `puf_vec_create` allocates and returns the device `Env` batch while binding device observation, action, reward, and terminal tensors;
- `puf_bind_stream` puts the environment on the trainer stream;
- `puf_step` advances the entire vector in CUDA kernels, as Breakout and Robot Arm do;
- PufferLib captures policy forward plus environment steps for the full horizon in one CUDA graph;
- device log reduction copies one aggregate `Log` to the host instead of all environment logs;
- evaluation alone copies environment 0 and its RDRAM to the host, matching the first-party pattern of device training plus host visualization;
- the CPU tensor shuttle and host vector-worker branches are not entered;
- a flat `float` observation ABI has compile-time `OBS_SIZE = 57`;
- five multidiscrete action heads have compile-time sizes `{15,9,2,2,2}`;
- internal frameskip gives one inference per two guest updates and ten decisions per simulated second;
- the same-stream device reset kernel preserves terminal transition buffers while autoresetting only marked environments;
- render-only terminal pause and persistent Shift+Up ownership leave headless training semantics unchanged;
- environment potential discount is coupled directly to learner gamma.

Wave Race differs from small first-party CUDA environments in scale. Each agent requires an isolated 8 MiB guest RDRAM mapping, so 4,096 agents allocate 32 GiB of physical RDRAM and reserve 16 TiB of GPU virtual address space. The accepted process used about 94.9 GB of 120 GB global GPU memory. This is an explicit occupancy and capacity tradeoff, not hidden framework overhead.

The current observation is compact rather than complete. It exposes the reward-potential inputs, target/pass geometry, velocity, recovery, body basis, 12 local water-height samples, native physics speed, and official power. Full RDRAM and the complete water field remain hidden. Strict Markov sufficiency is not claimed. OBS57 adds native speed and power after the unchanged OBS55 fields; loaders require a newly trained 57-input network.

The evaluator consumes an immutable, pointer-free projection containing rider kinematics, body basis, inputs, native clocks, lap splits, speed, power, route and terminal state, course nodes and signed pass points, plus a 33 by 33 local water tile. The renderer turns that projection into a custom low-poly scene and compact Wave Race-style Time Trials HUD. It replaces the rider and jet ski with the repository's 1,199,624-byte `resources/shared/puffer.glb`, SHA-256 `6e5e201b2d08c4eae48f04d9a715ef7b5e6dbb13bffa3c6903ea656730ce7644`, positioned and oriented by the authoritative body basis. It omits Championship rank and opponent portraits because the environment has one rider. Its 0.60 s filtered vertical camera anchor makes wave-relative Puffer motion visible. Model loading is lazy and confined to the evaluator; the renderer-free training path neither allocates `Client` nor opens the GLB. This is consistent with first-party Puffer environment design in separating compact training observations from an evaluation-only visualization, but visual polish itself is not evidence of simulation parity.

The configured reward uses official course topology and official miss/finish flags. Each new maximum route frontier earns credit once, following the dense distance-progress pattern used by Puffer's Drone racer while preventing oscillation from farming reward. Verified checkpoint credit parallels the discrete sector rewards in Whisker Racer. A route-node advance accompanied by a miss is not counted as a successful checkpoint. Game-driven teleports and recovery discontinuities do not create speed or progress reward. The success-driven per-environment lap curriculum follows established native Puffer curriculum patterns in Affine Lock, Bat, and Clifford.

The historical CPU adapter harness includes shortened one-lap and unmodified three-lap scripted fixtures through the public 57-value observation buffer. Current CUDA acceptance adds a CPU-oracle/device three-lap contract that finishes in 2,501 decisions, 5,002 native updates, and native time 250,041 ms with splits 83,624/82,908/83,509 ms. These scripted fixtures test reachability and transition equivalence; policy quality is established separately by current-checkpoint evaluation.

## Native CUDA implementation and boundary

The earlier conclusion that CPU-free simulation was infeasible within the static-recomp architecture did not survive implementation. Simply annotating the full host program would indeed have failed, but the production solution does more:

1. `generate_cuda_recomp.py` validates the exact ROM and computes the racing closure from the two per-frame entry points.
2. It emits 511 reachable game functions, 6 device runtime shims, and 510 indirect-dispatch entries instead of compiling all 1,203 host functions.
3. Exhaustive extraction covers 82 variable target addresses across four variable `LOOKUP_FUNC` caller sites. Unknown targets fail closed.
4. Each game update creates a fresh device `recomp_context`; no host `ucontext_t` or native stack is resumed.
5. Guest memory operations use the owning environment's device RDRAM base. CUDA VMM gives every environment a 4 GiB virtual slot with only its first 8 MiB mapped.
6. Host POSIX, DMA, controller, time, overlay, and fault behavior needed by the racing closure is replaced by bounded device shims and per-environment machine state.
7. Canonical reset RDRAM, variant page deltas, machine scalars, observations, actions, rewards, terminals, and logs remain device-resident.

The Wave Race device object is compiled with `--fmad=false --ftz=false --prec-div=true --prec-sqrt=true`. Policy and learner kernels are separate and retain normal CUDA contraction; SASS inspection confirmed fused multiply-add in the Muon learner. Headless training suppresses renderer-only water-normal display work, and the CPU/device contract verifies unchanged training transitions.

The boundary remains narrower than a full console port. Host startup still boots the cartridge to generate authentic reset states, and the human renderer is host-side. Graphics, audio, RSP/RDP output, menus during training, other riders, other courses, and other modes are not in the device closure. Direct independent Mupen parity remains limited to one held-A failure trace through the host oracle. CUDA is connected to that oracle by the measured transition contract, not by a blanket full-game parity proof.
