# Opponent attack observability

Inspection: 2026-09-17. Repository snapshot observed during the audit: `ba07f928f14a77588c1408d26091a641a094603b`. This was a source and existing-record review only. No game input, deployment, new hooks or runtime changes were performed for this audit. Exact local evidence paths, SHA-256 hashes, method identities and wire offsets are recorded in [opponent-action-observability.json](opponent-action-observability.json).

## Conclusion

The inspected client paths expose received hit effects, score awards and opponent poses. They do not expose a named opponent move, an authoritative action instance, or its execution interval. Existing passive records therefore support repeated received-hit observations while the player remains neutral. They do not establish repeated executions of the same named attack, or scored versus unscored windows for that attack.

Named attack causality requires authoritative opponent execution telemetry or a separately authorized controlled-player-attack design. More passive repetition alone cannot supply the missing action label or causal identifier. Neither new server instrumentation nor attacking-player control was authorized in this audit.

## Packet and callback boundary

| Inspected path | Payload available to the client | Missing identity |
| --- | --- | --- |
| `REK_Hit`, 29 bytes, unreliable | Contact position, normal, relative speed, kick flag | Fighter, victim, named move, action instance, body zone, impulse, server time |
| `REK_Score`, 7 bytes, reliable | Scoring slot, new hit count, points | Hit/action ID, move name, server time |
| `REK_Bones`, `2 + 28*N` bytes, unreliable | Network slot, bone count, positions and quaternions | Action ID, acceptance, source tick/time |
| `REK_FightState`, 33 bytes, reliable | Round, phase, score, result, human/fault/referee fields, AI level | Move/command ID, action acceptance; referee sequence is not an attack ID |
| `REK_Move`, 2 bytes | Actor network index and requested move index | Observed here as a local outbound request, without an opponent execution acknowledgement |

Recorder sequence counters are generated by the recorder. Wire-body hashes identify payload bytes. Neither supplies a native action-instance identifier.

Recovered `FightCoordinator.OnHitDetectedNetwork(HitEvent, ContactInfo)` projects richer server data into the 29-byte effects message. `HitEvent` includes attacker, hand, body zone, striker part, impulse and timestamp; `ContactInfo` includes robot/body/geometry references and a contact-pair key. Those identity/contact fields are absent from the transmitted projection. Even the inspected `HitEvent` constructor has no named clip or action-instance ID.

These recovered server-designated paths belong to the pinned client image.
The live server build and its implementation have not been verified. The field
projection describes that inspected code, with the received payload shape
checked empirically; it does not establish the server's internal runtime state.

`RobotInputController.TryNetworkInit()` registers the examined move/input handlers only on its server branch. `OnMoveMessageReceived` decodes the two-byte move request and executes a library entry locally on that path. This review found no corresponding server broadcast of opponent move executions to visual clients.

## Why local controller getters do not fill the gap

Recovered `Robot.EnterVisualOnlyMode()` disables the policy runner, `SonicMotionComposer`, synchronization and local MuJoCo components. `RobotInputController.IsPunching` reads local composer/action-runner state. `SonicMotionComposer.ActiveActionClip` reads the local active non-looping layer. `OnMoveExecuted(MocapClipConfig)` is a local execution callback in the inspected routes. None is established here as authoritative remote-AI execution telemetry. The recorder itself labels its local composer observation as having no exposed server acknowledgement or acceptance.

## Limits and next observation requirement

The reviewed inbound coverage is limited to the four schemas above, plus the move path and relevant local getters/visual setup. Other message families, including impact sound and notification paths, were not exhaustively audited. This is not a claim that every possible game protocol lacks an action ID. No inspected `PhysicsState` or physical-robot transport path was established as a remote AI action stream.

The current raw hit packet is unreliable. Missing received effects cannot establish a miss or an unscored attempt. Poses bracket client receipt rather than authoritative contact time; deployed raw packets lack QPC/UTC and must not be assigned invented server timestamps. A named-action repeat test needs authoritative actor/clip identity, action-instance boundaries, and a time or event linkage to contact and score outcomes. Without those, retain event-level labels such as received kick-tagged effect with same-frame opponent score, and leave named attack causality unknown.

The reviewed current recorder source hash is distinct from the deployed DLL hash. The empirical file reports version 0.7.2; current source is not asserted to be its exact build input. Packet fields were also checked in the actual records.
